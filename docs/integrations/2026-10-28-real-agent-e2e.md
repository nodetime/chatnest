# 真实模型端到端补验（2026-10-28）

目标：补齐 PDF、Excel、Todo、运行中停止和异常续跑的真实任务验证；不新增功能，不写死业务调用顺序。

## 环境与口径

| 项目 | 实际使用 |
|---|---|
| 应用 | 普通 ChatNest 预览，真实登录、PostgreSQL、本地私有文件存储；隔离验收账号，不修改用户聊天 |
| 模型 | 平台后台已配置的 `gpt-6.1-sol`，实际外部模型服务；未启用脚本模型、固定响应或浏览器请求替换 |
| 工具 | 实际 Porta HTTP MCP、原生参数、逐调用界面审批；模型自主加载技能、选择工具和创建产物 |
| 上游 | **仅本地合成供应商数据**；实际 Porta 的上游适配访问本地 HTTP 样本服务，不访问真实 1688 账号 |
| 故障 | 只在合成上游注入一次延迟或协议错误；不伪造模型回复、不直接替 Agent 执行工具 |
| 文件 | 两页中文文本 PDF、两工作表 XLSX；含不同单价、说明页和各自随机校验标记，全部为合成材料 |

## 本轮发现并修复

| 问题 | 最小修复 | 回归证据 |
|---|---|---|
| 中文文本 PDF 被误判为需要 OCR | 为 PDF.js 配置随依赖安装的本地 CMaps 与标准字体目录；不获取远程字体，不放宽解析限制 | 原中文 CID PDF 回归先失败后通过；同一原件重新上传后由真实模型读出两页 |
| 普通续问携带停止后的旧审批工具，首轮续问中断 | 只在本轮模型上下文剔除历史未完成工具；当前有效审批／Ask 续跑仍保留，已完成结果与失败保留；原始 UI／数据库审计不变 | SDK 转换回归覆盖旧审批排除、当前审批保留、终态保留及附件透传；真实新审批与产物保存通过 |
| 非 UTC 数据库中 user 与 assistant 时间相差四小时，重开排序错误 | raw SQL 用户消息及新对话时间统一使用与 Drizzle 相同的 UTC-naive 约定 | 独立临时 schema 在 America/New_York 会话中验证新对话时间及 user/assistant 交替顺序；新真实异常任务刷新后顺序正确 |

首轮失败不计为成功；旧消息时间没有批量改写。本轮恢复验证经过实际修复和正常用户续问，不改历史证据掩盖问题。

## 验收边界

- 本轮证明真实模型与真实应用／Porta MCP 的上述任务链路，不证明真实 1688 数据、扣费、限流或长期稳定性。
- PDF 为可提取文字的中文文件；扫描件 OCR、加密解锁、图片理解不在本轮。
- “继续”是新的正常用户轮次，由 Agent 决定下一步；不是后台持久任务、服务重启续流，也没有复用旧审批。
- 保持既有通用 Agent、Todo、Ask、工具范围和产物机制；不新增业务流程、恢复按钮或测试专用生产逻辑。
