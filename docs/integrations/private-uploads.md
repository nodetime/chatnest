# Private image attachments (local persistent driver)

This driver implements the existing JPEG/PNG conversation path. It does not implement document extraction, S3/cloud storage, or public object URLs. Original bytes, SHA-256 and sanitized UTF-8 display filenames are preserved. Decoding is only an integrity check; no re-encoding, resizing or silent modification occurs.

## Deployment

- Run a long-lived self-hosted Node process with PostgreSQL and a persistent private volume. Production requires an explicit **absolute** `UPLOAD_STORAGE_DIR`; startup upload capability remains unavailable if it is missing/relative. Development may use ignored `.data/private-uploads`.
- Directory and parents must not be symlinks. Keep the directory outside `public/`, static servers, reverse-proxy aliases and Next image optimization. Provision private owner-only directory permissions (0700); new files are created 0600 with exclusive/no-follow opens. The operator controls this path; do not allow other local accounts to mutate the directory/parents. Changing the path does not migrate existing files: copy/restore bytes and DB metadata together during maintenance.
- Apply `0002_private_uploads.sql` with the normal migration runner. It adds a disabled singleton configuration row, asset reservations and committed-message association records.
- Set the platform administrator UUID allowlist (see `.env.example`), open `/admin/storage`, test the real write/read/delete operation, then enable new uploads. No provider credentials are required or sent to the browser. Disable preserves existing attachment access; changing settings uses revision compare-and-swap.
- Defaults: `UPLOAD_USER_QUOTA_BYTES=104857600` (100 MiB), `UPLOAD_TOTAL_QUOTA_BYTES=1073741824` (1 GiB). Both must be integer byte counts between 5 MiB and 1 TiB. Reservations, including unfinished/deleting rows, count toward quotas until disk deletion succeeds. Quota reservation and draft count serialize across application processes with a PostgreSQL advisory transaction lock.
- Back up database metadata and the original-byte directory together; configure independent disk capacity monitoring. Filesystem and DB are not one atomic system: failed disk deletion retains a retryable `deleting` reservation instead of releasing quota for bytes still present. Interrupted pending uploads/drafts expire after 24 hours. Upload requests opportunistically process at most 10 cleanup records; administrator “清理过期草稿” processes at most 25. Run/trigger this bounded cleanup regularly even when uploads are idle. No external cron or cloud storage is installed by this patch.

## Current local scope and future adapters

The current storage boundary is `LocalUploadStore.write/read/delete`, called by the existing lifecycle service. Production uses a server-owned persistent volume at the absolute `UPLOAD_STORAGE_DIR`; there is no cloud adapter or provider registry yet, and the admin page deliberately has no selectable cloud provider. [Vercel Functions filesystem support](https://vercel.com/docs/functions/runtimes#file-system-support) is read-only except for `/tmp` scratch space; scratch space is not a durable replacement for this local volume.

A future private Blob adapter should use the [official Vercel Blob SDK and authentication configuration](https://vercel.com/docs/vercel-blob/using-blob-sdk), with an SDK version that supports private storage. Current documentation describes server-side OIDC/store configuration or read-write credentials; those credentials stay server-side. This requires real write/read/delete integration, preservation of existing application authorization, quotas, original-byte integrity and cleanup, plus migration/verification of old files and metadata. Changing an environment variable alone does not implement a provider or move existing data.

Agent configuration is separate from storage: this project already uses its own Zod-validated `config/agent.json`/`AGENT_CONFIG_PATH` conventions, HTTP MCP transport with `tools/list` and native tool schemas, and `SKILL.md` skill discovery. These are the project's existing contracts, not an invented universal Agent configuration standard; a future storage SDK integration does not replace them or turn autonomous tool/skill selection into fixed workflows.

## Limits and access

- One nonempty, verified JPEG/PNG per multipart request (`file`, `chatId` only). Maximum original file size 5 MiB; request body is stream-bounded to 5 MiB + 64 KiB before form parsing. MIME must match magic and successful decoder validation. Maximum decoded image area 16 million pixels; animated/multipage files are rejected. Per Node process at most four concurrent uploads and two image decodes are admitted without an unbounded queue. Put body/time/connection limits at the reverse proxy too.
- Chat JSON is authenticated before its stream is read; the full body is bounded to 1 MiB before JSON parsing, including approval continuation tool payloads. This accommodates 32,000-character text messages plus bounded tool data; image bytes never travel in client JSON. Oversize bodies receive 413 before model or persistence.
- 15 images per message on both client/server, plus a 20 MiB aggregate original-byte budget across the current model context, including history. Repeated references count repeatedly toward context bytes. Default maximum draft assets per user/intended-chat is 15.
- Only regular authenticated accounts upload or delete drafts; same-Origin is required. Owner-only drafts are tied to the intended chat UUID even before that chat exists. Existing chats must belong to the uploader. Asset filenames never become storage paths: UUIDs are the only locators.
- Authenticated readers (including guest sessions) may read a used image only when its intended chat exists and has a real committed message association. Its owner may read it; other readers require the chat to be **currently public**. Marking an asset `used` by itself grants no access. Switching a chat private immediately changes subsequent server reads; already downloaded client bytes cannot be revoked.
- GET returns `private, no-store`, `nosniff`, safe inline disposition and a restrictive CSP. Private previews use a direct authenticated `<img>` rather than Next Image's public optimizer/cache.
- Sending a new message atomically commits the chat/message, validates registration ownership/state and binds asset/message associations under the same lock used by draft DELETE. A deletion that wins first makes sending fail cleanly; a committed association makes draft DELETE return 409. Used files are never deleted by draft cleanup. Chat deletion cleans local assets best-effort; failed deletes retain retryable metadata. Unassociated used orphans remain private/inaccessible and quota-counted for operator reconciliation.

## Model delivery and compatibility

Only same-origin canonical relative `/api/files/<UUID>` references are accepted (`/demo/api/files/<UUID>` under the demo basePath). Old external/public URLs, data URLs supplied by clients, and arbitrary remote URLs are explicitly rejected rather than downloaded, migrated or deleted. The server checks **all** canonical incoming/history attachments, ownership, original byte count/hash and model vision support before chat/message persistence, title generation or model calls. Canonical references stay in the DB/UI; only the server's model prompt receives inline original-byte data URLs. Approval continuations/regeneration continue using the canonical DB history merge. Editing reconstructs the stored prefix and original immutable file parts with the new text, without deleting history before validation. Only successful completion replaces the text/answer and later tail in a snapshot-checked transaction; the edited user row and its attachment association remain intact. Client validation/model/abort failures restore the original optimistic history and preserve the edit draft.

`@ai-sdk/openai` 4.0.7 Chat Completions serialization emits bare base64 for V4 image `data` parts. A narrow `wrapLanguageModel` V4 middleware in `lib/ai/inline-image-middleware.ts` converts only inline PNG/JPEG data parts into URL-tagged complete data URLs after SDK normalization and before the provider converter. Responses and gateway models are unchanged. `tests/unit/openai-inline-images.test.ts` captures actual provider request JSON for PNG and JPEG and asserts complete data URLs and unchanged bytes. Retain this wire regression when upgrading/removing the compatibility shim.

Client submission checks pending upload admission synchronously, invalidates old generations on every chat switch/unmount, aborts pending upload requests and ignores stale callbacks (including A→B→A). Selected attachments/text remain until successful completion; server-side capability/attachment errors preserve the draft. Removing/abandoning drafts requests safe owner-only deletion; unknown completions from aborted requests fall back to expiry cleanup.

## Verification boundaries

Offline tests use synthetic images, temporary private directories, injected resolvers and an injected mock provider fetch; they make no supplier/model requests. Independent local PostgreSQL/HTTP/browser/mock-model evidence is maintained by the verification owner outside tracked fixtures. This does not prove acceptance by a paid production model or compatibility with ephemeral cloud deployments. PDF, Word and Excel parsing are separate work.

## Known concurrency boundary

Edited-turn replacement is snapshot checked and retains the original user's attachment association. The existing ordinary-stream completion path does not introduce a global chat run/version fence against edits from another tab; that broader concurrency coordination remains separate work. This does not relax attachment authorization or allow draft deletion of a committed attachment.
