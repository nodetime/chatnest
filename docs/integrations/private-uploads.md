# 私有附件（本地持久化驱动）

此驱动支持 JPEG/PNG 图片，以及从 PDF、DOCX、XLSX、CSV 和 UTF-8 TXT 中提取文本。存储保持本地、私有：不上传云端，不提供 OCR、密码处理或公开对象 URL。原始字节、SHA-256 和经过安全清理的 UTF-8 显示文件名均予保留。解码仅用于完整性检查；不会重新编码、调整尺寸或静默修改内容。

## 部署

- 运行长期驻留的自托管 Node 进程，配合 PostgreSQL 和持久化私有卷。生产环境必须显式设置**绝对路径** `UPLOAD_STORAGE_DIR`；若缺失或为相对路径，启动后的上传能力保持不可用。开发环境可使用已被忽略的 `.data/private-uploads`。本地驱动明确拒绝 `VERCEL=1`，返回 503，包括使用绝对 `/tmp` 路径的情况；能力报告保持不可用，写入/读取/删除测试也不能据此声称具备持久化存储能力。
- 目录及其父目录不得为符号链接。目录应置于 `public/`、静态服务器、反向代理别名和 Next 图片优化范围之外。为目录配置仅属主可访问的私有权限（0700）；新文件以 0600 权限创建，打开时采用独占创建、禁止跟随符号链接的方式。此路径由运维人员控制；不得允许其他本地账户修改该目录或其父目录。修改路径不会迁移现有文件：维护期间必须同时复制/恢复原始字节和数据库元数据。
- 使用常规迁移执行器应用 `0002_private_uploads.sql`。它会添加一条默认禁用的单例配置记录、资产预留记录和已提交消息关联记录。
- 设置平台管理员 UUID 白名单（见 `.env.example`），打开 `/admin/storage`，测试真实写入/读取/删除操作，然后启用新上传。无需供应商凭据，也不会向浏览器发送此类凭据。禁用上传会保留对已有附件的访问；修改设置采用修订号比较并交换机制。
- 默认值：`UPLOAD_USER_QUOTA_BYTES=104857600`（100 MiB），`UPLOAD_TOTAL_QUOTA_BYTES=1073741824`（1 GiB）。两者都必须是 5 MiB 至 1 TiB 之间的整数字节数。预留记录（包括未完成/删除中的记录）在磁盘删除成功前均计入配额。配额预留和草稿数量通过 PostgreSQL 事务级咨询锁在不同应用进程之间串行处理。
- 数据库元数据与原始字节目录必须一并备份；另行配置磁盘容量监控。文件系统和数据库并非同一个原子系统：磁盘删除失败时会保留可重试的 `deleting` 预留记录，而不是为仍然存在的字节释放配额。中断的待处理上传/草稿在 24 小时后过期。上传请求会顺便处理最多 10 条清理记录；管理员“清理过期草稿”操作最多处理 25 条。即使没有上传活动，也要定期运行/触发这种有数量上限的清理。此补丁不会安装外部定时任务或云存储。

## 当前本地范围与未来适配器

当前存储边界是 `LocalUploadStore.write/read/delete`，由现有生命周期服务调用。生产环境使用服务端管理的持久化卷，路径为绝对路径 `UPLOAD_STORAGE_DIR`；目前尚无云适配器或供应商注册表，管理页面也有意不提供可选的云供应商。[Vercel Functions 文件系统支持](https://vercel.com/docs/functions/runtimes#file-system-support)除 `/tmp` 临时空间外均为只读；临时空间不能作为此本地卷的持久化替代。临时空间写入/读取/删除成功只能验证当前实例，不能验证跨实例或跨调用的持久性；本地驱动会在探测文件系统前拒绝这种部署方式。

未来的私有 Blob 适配器应使用[官方 Vercel Blob SDK 和认证配置](https://vercel.com/docs/vercel-blob/using-blob-sdk)，且 SDK 版本必须支持私有存储。当前文档描述了服务端 OIDC/存储配置或读写凭据；这些凭据必须留在服务端。Functions 上的大附件需要经过身份认证的**直接上传到私有对象存储**适配器，而不能通过函数请求体传输字节。这需要真实的写入/读取/删除集成，保留应用现有的授权、配额、原始字节完整性和清理机制，并迁移/验证旧文件及元数据。当前本地驱动尚未实现该适配器及其验收测试。仅修改环境变量并不能实现供应商支持，也不会迁移现有数据。

Agent 配置与存储分离：本项目已经使用自身经 Zod 校验的 `server/infrastructure/mcp/agent.json`/`AGENT_CONFIG_PATH` 约定、带有 `tools/list` 和原生工具 schema 的 HTTP MCP 传输，以及 `SKILL.md` 技能发现机制。这些是项目既有契约，并非虚构的通用 Agent 配置标准；未来的存储 SDK 集成不会替代这些契约，也不会将自主工具/技能选择变成固定工作流。

## 限制与访问

- 每个 multipart 请求只允许一个非空、经验证的附件（仅含 `file`、`chatId`）。图片上限仍为 5 MiB；文档上限为 64 MiB。在表单解析前，以流式方式将 multipart 请求体限制为 64 MiB + 64 KiB。MIME 必须与魔数匹配，并通过解码器验证。解码后的图片面积最多为 16 百万像素；拒绝动画/多页文件。每个 Node 进程最多接纳四个并发上传和两个图片解码，不使用无界队列。反向代理也应配置请求体/时间/连接限制。
- 读取聊天 JSON 流前先进行身份认证；JSON 解析前将完整请求体限制为 1 MiB，包括审批续接中的工具载荷。这可容纳 32,000 字符的文本消息及有界工具数据；图片字节绝不通过客户端 JSON 传输。超大请求体会在模型调用或持久化之前收到 413。
- 客户端和服务端均限制每条消息最多 15 个附件（因此图片仍最多为 15 张），同时当前模型上下文（包括历史）中的图片原始字节总预算为 20 MiB。重复引用会重复计入上下文字节数。每个用户/目标聊天的草稿资产默认上限为 15。
- 仅已认证的普通账户可上传或删除草稿；必须同源。仅属主可访问的草稿在目标聊天尚未创建前就已绑定该聊天的 UUID。已有聊天必须属于上传者。资产文件名绝不会变成存储路径：UUID 是唯一定位符。
- 已认证的读取者（包括访客会话）只有在目标聊天存在且有真实的已提交消息关联时，才能读取已使用的图片。其属主可以读取；其他读取者则要求聊天**当前为公开状态**。仅将资产标记为 `used` 本身不会授予访问权限。将聊天切换为私有会立即影响后续服务端读取；客户端已下载的字节无法撤回。
- GET 返回 `private, no-store`、`nosniff`、安全的图片内联显示/文档下载处置方式，以及严格的 CSP。私有预览使用直接经过身份认证的 `<img>`，而不是 Next Image 的公开优化器/缓存。
- 发送新消息时，会在与草稿 DELETE 相同的锁下，原子提交聊天/消息、验证注册记录的归属/状态，并绑定资产/消息关联。若删除先获得锁，发送会明确失败；若关联已提交，草稿 DELETE 返回 409。草稿清理绝不会删除已使用的文件。删除聊天时会尽力清理本地资产；删除失败会保留可重试的元数据。没有关联的已使用孤立资产仍保持私有、不可访问，并继续计入配额，等待运维人员核对处理。

## 模型传递与兼容性

仅接受同源、规范的相对引用 `/api/files/<UUID>`（在演示 basePath 下为 `/demo/api/files/<UUID>`）。旧的外部/公开 URL、客户端提供的 data URL 和任意远程 URL 都会被明确拒绝，不会下载、迁移或删除它们。在聊天/消息持久化、标题生成或模型调用前，服务端会检查**所有**传入及历史中的规范附件、归属、原始字节数/哈希，以及图片所需的模型视觉支持。数据库/UI 中保留规范引用；仅服务端准备的图片部分会接收包含原始字节的内联 data URL。文档以序列化的不可信文本预览形式传递，绝不使用原生 PDF URL 或二进制内容。审批续接/重新生成继续使用规范的数据库历史合并机制。编辑时会用新文本重建已存储的前缀和原始不可变文件部分，不会在验证前删除历史。只有成功完成后，才会在经过快照校验的事务中替换文本/回答及后续尾部历史；被编辑的用户记录及其附件关联保持完整。客户端验证/模型/中止失败会恢复原有的乐观更新历史，并保留编辑草稿。

`@ai-sdk/openai` 4.0.7 的 Chat Completions 序列化会为 V4 图片 `data` 部分输出裸 base64。`server/application/ai/inline-image-middleware.ts` 中一个作用范围很窄的 `wrapLanguageModel` V4 中间件，会在 SDK 规范化之后、供应商转换器之前，仅将内联 PNG/JPEG 数据部分转换为带 URL 类型标记的完整 data URL。Responses 和网关模型保持不变。`server/application/ai/openai-inline-images.test.ts` 会捕获 PNG 和 JPEG 的实际供应商请求 JSON，断言 data URL 完整且字节未变。升级/移除兼容垫片时，应保留这项传输回归测试。

客户端提交时会同步检查待处理上传的准入状态，在每次切换聊天/卸载时使旧代次失效，中止待处理上传请求，并忽略过期回调（包括 A->B->A）。选中的附件/文本会保留到成功完成；服务端能力/附件错误会保留草稿。移除/放弃草稿会请求安全的仅属主删除；已中止请求若有未知完成结果，则由过期清理兜底。

## 验证边界

离线测试使用合成图片、临时私有目录、注入的解析器，以及注入的模拟供应商 fetch；不会发起供应商/模型请求。独立的本地 PostgreSQL/HTTP/浏览器/模拟模型证据由验证负责人维护，置于版本跟踪夹具之外。这不能证明已通过付费生产模型验收，也不能证明与临时云部署兼容。文档单元测试覆盖使用生成的合成 PDF、DOCX、XLSX、CSV 和 TXT 夹具；不会访问用户文档。重新打开已完成并持久化的消息/产物，与重新连接正在生成的内容是两回事。当前 `GET /api/chat/[id]/stream` 处理器始终返回 **204 No Content**；**尚未实现**生成中内容的恢复/重放。仅设置 `REDIS_URL` 并不会启用此能力。重开已完成历史不能作为生成中流重连的证据。

## 已知并发边界

编辑轮次的替换会进行快照校验，并保留原用户消息的附件关联。现有普通流完成路径并未引入全局聊天运行/版本屏障来防范其他标签页的编辑；更广泛的并发协调仍是独立工作。这不会放宽附件授权，也不会允许通过草稿删除来删除已提交的附件。


## 文档提取 / Agent 读取契约

- 运行时前提为 Node `>=22.13.0 || >=24`；已使用 Node 24.20.0 独立验证。解析依赖从官方 npm 注册表锁定：`pdfjs-dist@6.4.299`、`mammoth@1.13.0`、`exceljs@4.4.0`、`yauzl@3.4.0`，以及流式 OOXML 元数据扫描器 `saxes@6.0.0`（安装使用 `--ignore-scripts`）。公开 API 来源：[PDF.js](https://github.com/mozilla/pdf.js)、[Mammoth](https://github.com/mwilliamson/mammoth.js)、[ExcelJS 流式读取器](https://github.com/exceljs/exceljs#streaming-xlsx-reader)、[yauzl](https://github.com/thejoshwolfe/yauzl)。
- worker 是已纳入版本控制的独立文件 `server/infrastructure/uploads/document-worker.cjs`，通过 Next 输出追踪为 `/api/files/upload` 显式包含该文件及其依赖。仅构建时使用的 `@vercel/nft@1.11.0` 会在 `PHASE_PRODUCTION_BUILD` 阶段追踪 worker 和 PDF.js 原生 canvas 依赖闭包；PDF.js 通过计算确定的 worker/maps/fonts 会在实际解析出的包路径下单独包含。必须在目标部署操作系统/架构上构建，使追踪到的原生二进制与之匹配。针对外部解析包，宿主端字面量 `require.resolve` 追踪入口也能让 Next 的原生路由追踪保留 pnpm 目录解析符号链接：单独使用 `outputFileTracingIncludes` 会将目录链接视为 `nodir` 而丢弃。这些追踪入口仅解析入口路径，不会在宿主中初始化解析器。追踪器不会在每次上传时或 `next start` 期间加载。它不需要 TypeScript 加载器、继承的 `NODE_OPTIONS`、应用环境或模型凭据。除单元/TypeScript 检查外，还必须对生产产物的干净副本执行上传冒烟验证。隔离验证期间不得运行 `pnpm build`：该包装命令会迁移其环境所选择的数据库。
- 每个 Node 进程仅允许一个解析器，繁忙时拒绝而不是排队。低成本的存储启用/配置/聊天属主/原始字节配额/草稿数量检查先于昂贵解析；第二次持有咨询锁的事务会在预留前原子检查全部原始字节与实际派生字节。四个请求体上传和两个图片解码器仍分别受限。反向代理应配置请求/时间/连接限制。
- 每个 worker 都有一个由父进程管理、权限为 0700 的 `chatnest-document-*` 临时目录，受限环境（仅 `NODE_ENV`、`TMPDIR`、`TMP`、`TEMP`）、空 `execArgv`、256/32 MiB 的 V8 老生代/新生代堆限制、4 MiB 栈，以及 20 秒终止期限。无论成功、解析器报错、无响应且以零状态退出、启动失败还是超时，父进程都会终止 worker 并移除其临时目录。V8 限制**并不是** RSS/原生缓冲区/网络沙箱：部署时应使用容器，显式配置 CPU、内存、临时磁盘和日志预算，预留宿主机余量并监控实际限制。不接受任意文件或 URL 作为解析器输入。
- 原始输入硬上限为 64 MiB；ZIP 最多 4096 个条目，声明的**以及实际的**解压总量（含嵌入媒体）最多 128 MiB，单个 XML 最多 32 MiB / XML 总量最多 64 MiB。预检会流式读取每个条目、验证 CRC，并拒绝重复/路径穿越/加密路径、本地头与中央目录头不一致、隐藏/未索引记录、DTD/实体、其他 XML 编码，以及宏/嵌入对象包。预算限制在任一 Office 解析器运行前生效。
- PDF 文本使用 `pdfjs-dist/legacy/build/pdf.mjs` 提取，禁用求值、系统字体和外部获取；最多 300 页。`page:N` 引用对应实际 PDF 页码。加密 PDF 返回 `locked`（无密码输入/状态）；纯扫描 PDF 返回 `no_extractable_text`；混合文档中的空白页有明确警告。不执行 OCR。
- DOCX 引用对应真实且有序的 `paragraph:N` 或 `table:N:row:N:cell:N:paragraph:N`，不是虚构页码。Mammoth 1.13.0 的 `extractRawText` 不接受转换函数，且会丢失表格位置。因此，实现使用公开 `convertToHtml` 的带类型 `transformDocument` 钩子收集纯文本，然后在转换前返回一棵**空**树，并设置 `externalFileAccess:false`。不会渲染、存储或向模型发送源 HTML 或图片转换结果。文本提取明确不解读嵌入媒体/图表。
- XLSX 使用**流式** `ExcelJS.stream.xlsx.WorkbookReader`，绝不使用 `xlsx.load`。已验证的 XML 会以有界流重新输出，工作簿元数据在前；原始字节不变。媒体已经由预检流式读取并排空，在仅供解析器使用的流中省略。缺失共享字符串表时会插入一个固定的空表，避免 ExcelJS 4.4.0 的延迟工作表/临时文件路径造成数据丢失。这也避免了其工作表先于工作簿时的顺序竞态。有界 SAX 遍历会解析每个真实的工作簿工作表关系（包括自定义/绝对部件路径），保留真实工作表名称和 date1904，并映射到仅供解析器使用的规范名称。工作表关系缺失、指向外部或不受支持时会明确失败，而非静默丢弃工作表。宏检测检查 ContentType/关系元数据和真实包条目名称，不检查普通文档正文。库创建的任何临时工作表仍留在私有 `TMPDIR`；其磁盘总预算受原始 XML 总量限制。最多 50 张工作表和 100,000 个非空单元格；`sheet:"name"!A1` 引用保留稀疏位置。公式**仅读取缓存结果**，缺失结果有明确标记；绝不执行或获取公式/宏/链接。日期为 ISO 文本。嵌入图片/图表不会作为视觉内容读取。
- CSV 保留实际解析出的行号，包括带引号的多行字段；对于合法的单列/单单元格文件，无法检测分隔符时会给出警告并默认使用逗号，而引号格式错误仍会报错；TXT 使用 UTF-8 行引用。DOC/XLS 和宏格式必须转换成普通受支持文件。Office 加密/旧版二进制容器会要求提供已解密的现代格式副本；服务端不提供解密，也不存储密码。
- 持久化提取结果最多为 1,000,000 个 JS 字符或 20,000 个分段，每段最多 4000 字符，并具有明确的 `truncated` 状态。被丢弃的内容不能通过隐藏途径取回。`UploadAsset.extraction` 存储 `{status,characters,segments:[{ref,text}],warnings}`；实际 JSON UTF-8 字节长度存为 `derivedBytes`（最多 8 MiB），且**原始字节 + 派生字节**均计入部署/用户配额，包括待处理/删除中的预留记录。因此，体积很小的压缩文件也不能生成未计入配额的持久化文本。迁移 `0003_document_ingestion` 扩展现有表/生命周期；数据库提取结果与原始目录应一并备份。
- 上传响应新增 `size` 和 `extraction:{status,characters,segments:number,warnings}`；规范引用保持不变。UI 显示上传中/读取中、文本就绪、已截断、已锁定/无文本或失败状态，并包含文件名/类型/大小。失败重试仅保留临时浏览器 `File`，绝不保留密码。已锁定/扫描件/失败的附件禁止发送，可移除/替换。原始图片和编辑关联仍予保留。
- 一个可信适配器统一覆盖新消息/历史/重新生成/审批/编辑上下文，在持久化/标题/模型调用前执行。每个文档都会获得一份 JSON 序列化的 `UNTRUSTED_ATTACHMENT_SOURCE` 预览，最多含 2000 个源字符、资产元数据、真实引用、源统计/状态，以及仅文本/无 OCR/无媒体分析的说明。重复规范引用共用一份预览。一轮中的预览源文本总上限为 100,000 字符；超出上下文时会明确失败。服务端以流式方式校验原件完整性，不会将大型文档二进制保留在模型上下文内存中。只有图片需要视觉能力。不支持工具的模型会收到明确的有限预览说明，不会暗示已经全文读取。
- 可选的 `readAttachment({assetId,startSegment=0,limit=20})` 接受从零开始的分段偏移，以及 1..100 个分段。每次调用都会重新检查当前用户、聊天归属、`used` 状态，以及真实的规范已提交消息关联；草稿/公开/跨聊天 ID 不构成工具访问权限。它返回资产/名称/状态/警告/统计、`segments:[{ref,text}]`、`nextSegment` 或 null、字符数和剩余预算。每次调用最多返回 16,000 个源字符。一个由服务端管理的共享 `AttachmentRoundBudget` 将**所有附件合计**限制为每轮模型调用 100,000 个源字符，初始消耗取自适配器实际消费的去重预览文本（不是每个资产的固定预留）。工具读取会在所有资产之间消耗同一份剩余预算。它绝不会跳过部分分段；若剩余预算不足以容纳下一个分段，会明确说明，而不是返回无限空页。由模型选择的读取是可选能力，不是关键词/供应商/表格流水线。
- 当前流步骤会收到真实源文本。在**新请求**中，历史 `readAttachment` 输出会在模型投影中变为 `HISTORICAL_ATTACHMENT_READ_METADATA`（资产/名称/状态、字符/范围元数据，以及明确的“源文本不会重放；可按需重新读取”说明）。这防止历史原始文本无限重放。规范数据库/UI 输出保持不变；附件读取卡片显示可读的文本/引用详情。该请求中的新调用仍会收到实际源分段。


### Next 代理请求体封装与内存预算

已安装的 Next 16.2.10 使用 `experimental.proxyClientMaxBodySize`（旧名称 `middlewareClientMaxBodySize` 已弃用）。值设为 **65mb**，以容纳应用的 64 MiB 文档 + 64 KiB multipart 封装，避免 Next 按其 10 MB 默认值静默截断。图片验证上限仍为 5 MiB，文档验证上限仍为 64 MiB，同源/身份认证/应用准入保持生效；不会绕过代理。参见 [Next 官方代理请求体文档](https://nextjs.org/docs/app/api-reference/config/next-config-js/proxyClientMaxBodySize)。

Next 设置仅作用于其自身的代理缓冲区。[Vercel Functions 对请求/响应载荷设有 4.5 MB 限制](https://vercel.com/docs/functions/limitations#request-body-size)；**65mb 不会提高该平台限制**，也不会使 64 MiB multipart 上传在 Functions 上可用。当前本地驱动仅适用于自托管；云部署需要上文所述的私有直传适配器。

Next 会在**路由级准入之前**复制请求体，其限制按单个请求生效，并非全局信号量。生产容器 RSS 预算除四个已获准的应用请求体、解析器 V8/原生缓冲区及 Next 本身外，还应计入这些副本。前置代理也应实施连接/速率/请求体/并发/时间预算；仅靠 V8 `resourceLimits` 和应用准入并不能防护总 RSS。部署限制必须在实际宿主机上验证，不能从本地解析器测试成功推断得出。


## AI 遥测内容边界

`instrumentation.ts` 全局注册了 AI SDK OpenTelemetry 集成。在已安装的 `ai@7.0.15` 中，已注册的集成默认启用，输入/输出记录也默认开启。因此，应用的每次模型调用都会显式应用冻结的 `server/shared/telemetry.ts` 策略：`recordInputs:false` 和 `recordOutputs:false`。这包括主聊天、标题生成、文本/代码/表格创建与更新，以及建议（九处调用），并非仅限顶层聊天流。

该策略保留模型/用量/耗时等运行元数据，但不会将提示词、附件预览、文档正文、工具输入/结果或生成内容记录为 AI 输入/输出 span 属性。离线测试会检查所有调用点，并使用本地模拟模型/工具和捕获的 span 属性验证已安装的 AI SDK 与 OTel。这并不代表对应用日志、供应商端留存、传输错误或第三方埋点进行了全面脱敏；部署前应分别审查这些内容。
