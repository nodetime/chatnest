# Private attachments (local persistent driver)

This driver supports JPEG/PNG images and text extraction from PDF, DOCX, XLSX, CSV and UTF-8 TXT. Storage stays local/private: no cloud upload, OCR, password handling or public object URLs. Original bytes, SHA-256 and sanitized UTF-8 display filenames are preserved. Decoding is only an integrity check; no re-encoding, resizing or silent modification occurs.

## Deployment

- Run a long-lived self-hosted Node process with PostgreSQL and a persistent private volume. Production requires an explicit **absolute** `UPLOAD_STORAGE_DIR`; startup upload capability remains unavailable if it is missing/relative. Development may use ignored `.data/private-uploads`. The local driver explicitly rejects `VERCEL=1` with 503, including absolute `/tmp` paths; capability reporting stays unavailable and the write/read/delete test cannot claim durable storage there.
- Directory and parents must not be symlinks. Keep the directory outside `public/`, static servers, reverse-proxy aliases and Next image optimization. Provision private owner-only directory permissions (0700); new files are created 0600 with exclusive/no-follow opens. The operator controls this path; do not allow other local accounts to mutate the directory/parents. Changing the path does not migrate existing files: copy/restore bytes and DB metadata together during maintenance.
- Apply `0002_private_uploads.sql` with the normal migration runner. It adds a disabled singleton configuration row, asset reservations and committed-message association records.
- Set the platform administrator UUID allowlist (see `.env.example`), open `/admin/storage`, test the real write/read/delete operation, then enable new uploads. No provider credentials are required or sent to the browser. Disable preserves existing attachment access; changing settings uses revision compare-and-swap.
- Defaults: `UPLOAD_USER_QUOTA_BYTES=104857600` (100 MiB), `UPLOAD_TOTAL_QUOTA_BYTES=1073741824` (1 GiB). Both must be integer byte counts between 5 MiB and 1 TiB. Reservations, including unfinished/deleting rows, count toward quotas until disk deletion succeeds. Quota reservation and draft count serialize across application processes with a PostgreSQL advisory transaction lock.
- Back up database metadata and the original-byte directory together; configure independent disk capacity monitoring. Filesystem and DB are not one atomic system: failed disk deletion retains a retryable `deleting` reservation instead of releasing quota for bytes still present. Interrupted pending uploads/drafts expire after 24 hours. Upload requests opportunistically process at most 10 cleanup records; administrator “清理过期草稿” processes at most 25. Run/trigger this bounded cleanup regularly even when uploads are idle. No external cron or cloud storage is installed by this patch.

## Current local scope and future adapters

The current storage boundary is `LocalUploadStore.write/read/delete`, called by the existing lifecycle service. Production uses a server-owned persistent volume at the absolute `UPLOAD_STORAGE_DIR`; there is no cloud adapter or provider registry yet, and the admin page deliberately has no selectable cloud provider. [Vercel Functions filesystem support](https://vercel.com/docs/functions/runtimes#file-system-support) is read-only except for `/tmp` scratch space; scratch space is not a durable replacement for this local volume. A successful scratch write/read/delete would test only the current instance, not persistence across instances or invocations; the local driver rejects that deployment before filesystem probing.

A future private Blob adapter should use the [official Vercel Blob SDK and authentication configuration](https://vercel.com/docs/vercel-blob/using-blob-sdk), with an SDK version that supports private storage. Current documentation describes server-side OIDC/store configuration or read-write credentials; those credentials stay server-side. Large attachments on Functions require an authenticated **direct-to-private-object-storage upload** adapter rather than sending bytes through the function request body. This requires real write/read/delete integration, preservation of existing application authorization, quotas, original-byte integrity and cleanup, plus migration/verification of old files and metadata. That adapter and its acceptance tests are not implemented by the current local driver. Changing an environment variable alone does not implement a provider or move existing data.

Agent configuration is separate from storage: this project already uses its own Zod-validated `server/infrastructure/mcp/agent.json`/`AGENT_CONFIG_PATH` conventions, HTTP MCP transport with `tools/list` and native tool schemas, and `SKILL.md` skill discovery. These are the project's existing contracts, not an invented universal Agent configuration standard; a future storage SDK integration does not replace them or turn autonomous tool/skill selection into fixed workflows.

## Limits and access

- One nonempty, verified attachment per multipart request (`file`, `chatId` only). Images remain capped at 5 MiB; documents are capped at 64 MiB. Multipart request bodies are stream-bounded to 64 MiB + 64 KiB before form parsing. MIME must match magic and successful decoder validation. Maximum decoded image area 16 million pixels; animated/multipage files are rejected. Per Node process at most four concurrent uploads and two image decodes are admitted without an unbounded queue. Put body/time/connection limits at the reverse proxy too.
- Chat JSON is authenticated before its stream is read; the full body is bounded to 1 MiB before JSON parsing, including approval continuation tool payloads. This accommodates 32,000-character text messages plus bounded tool data; image bytes never travel in client JSON. Oversize bodies receive 413 before model or persistence.
- 15 attachments per message on both client/server (so still at most 15 images), plus a 20 MiB aggregate image original-byte budget across the current model context, including history. Repeated references count repeatedly toward context bytes. Default maximum draft assets per user/intended-chat is 15.
- Only regular authenticated accounts upload or delete drafts; same-Origin is required. Owner-only drafts are tied to the intended chat UUID even before that chat exists. Existing chats must belong to the uploader. Asset filenames never become storage paths: UUIDs are the only locators.
- Authenticated readers (including guest sessions) may read a used image only when its intended chat exists and has a real committed message association. Its owner may read it; other readers require the chat to be **currently public**. Marking an asset `used` by itself grants no access. Switching a chat private immediately changes subsequent server reads; already downloaded client bytes cannot be revoked.
- GET returns `private, no-store`, `nosniff`, safe inline image / download document disposition and a restrictive CSP. Private previews use a direct authenticated `<img>` rather than Next Image's public optimizer/cache.
- Sending a new message atomically commits the chat/message, validates registration ownership/state and binds asset/message associations under the same lock used by draft DELETE. A deletion that wins first makes sending fail cleanly; a committed association makes draft DELETE return 409. Used files are never deleted by draft cleanup. Chat deletion cleans local assets best-effort; failed deletes retain retryable metadata. Unassociated used orphans remain private/inaccessible and quota-counted for operator reconciliation.

## Model delivery and compatibility

Only same-origin canonical relative `/api/files/<UUID>` references are accepted (`/demo/api/files/<UUID>` under the demo basePath). Old external/public URLs, data URLs supplied by clients, and arbitrary remote URLs are explicitly rejected rather than downloaded, migrated or deleted. The server checks **all** canonical incoming/history attachments, ownership, original byte count/hash and model vision support for images before chat/message persistence, title generation or model calls. Canonical references stay in the DB/UI; only server-prepared image parts receive inline original-byte data URLs. Documents are serialized untrusted text previews, never native PDF URLs or binary content. Approval continuations/regeneration continue using the canonical DB history merge. Editing reconstructs the stored prefix and original immutable file parts with the new text, without deleting history before validation. Only successful completion replaces the text/answer and later tail in a snapshot-checked transaction; the edited user row and its attachment association remain intact. Client validation/model/abort failures restore the original optimistic history and preserve the edit draft.

`@ai-sdk/openai` 4.0.7 Chat Completions serialization emits bare base64 for V4 image `data` parts. A narrow `wrapLanguageModel` V4 middleware in `server/application/ai/inline-image-middleware.ts` converts only inline PNG/JPEG data parts into URL-tagged complete data URLs after SDK normalization and before the provider converter. Responses and gateway models are unchanged. `server/application/ai/openai-inline-images.test.ts` captures actual provider request JSON for PNG and JPEG and asserts complete data URLs and unchanged bytes. Retain this wire regression when upgrading/removing the compatibility shim.

Client submission checks pending upload admission synchronously, invalidates old generations on every chat switch/unmount, aborts pending upload requests and ignores stale callbacks (including A→B→A). Selected attachments/text remain until successful completion; server-side capability/attachment errors preserve the draft. Removing/abandoning drafts requests safe owner-only deletion; unknown completions from aborted requests fall back to expiry cleanup.

## Verification boundaries

Offline tests use synthetic images, temporary private directories, injected resolvers and an injected mock provider fetch; they make no supplier/model requests. Independent local PostgreSQL/HTTP/browser/mock-model evidence is maintained by the verification owner outside tracked fixtures. This does not prove acceptance by a paid production model or compatibility with ephemeral cloud deployments. Document unit coverage uses generated synthetic PDF, DOCX, XLSX, CSV and TXT fixtures; no user documents are accessed. Reopening completed persisted messages/artifacts is distinct from reconnecting to an in-progress generation. The current `GET /api/chat/[id]/stream` handler always returns **204 No Content**; in-progress generation resume/replay is **not implemented**. Setting `REDIS_URL` alone does not enable it. Completed-history reopening is not evidence of in-flight stream reconnection.

## Known concurrency boundary

Edited-turn replacement is snapshot checked and retains the original user's attachment association. The existing ordinary-stream completion path does not introduce a global chat run/version fence against edits from another tab; that broader concurrency coordination remains separate work. This does not relax attachment authorization or allow draft deletion of a committed attachment.


## Document extraction / Agent reading contract

- Runtime prerequisite is Node `>=22.13.0 || >=24`; independently exercised with Node 24.20.0. Parser dependencies are pinned from the official npm registry: `pdfjs-dist@6.4.299`, `mammoth@1.13.0`, `exceljs@4.4.0`, `yauzl@3.4.0`, plus streaming OOXML metadata scanner `saxes@6.0.0` (installation uses `--ignore-scripts`). Public API sources: [PDF.js](https://github.com/mozilla/pdf.js), [Mammoth](https://github.com/mwilliamson/mammoth.js), [ExcelJS streaming reader](https://github.com/exceljs/exceljs#streaming-xlsx-reader), [yauzl](https://github.com/thejoshwolfe/yauzl).
- The worker is a checked-in standalone `server/infrastructure/uploads/document-worker.cjs`, explicitly included by Next output tracing for `/api/files/upload`, with its dependencies. Build-only `@vercel/nft@1.11.0` traces the worker plus PDF.js's native canvas dependency closure in `PHASE_PRODUCTION_BUILD`; PDF.js's computed worker/maps/fonts are included separately at the real resolved package path. Build on the intended deployment OS/architecture so the traced native binary matches it. Literal host `require.resolve` seeds for external parser packages also let Next's native route tracing preserve pnpm directory resolution symlinks: `outputFileTracingIncludes` alone treats directory links as `nodir` and drops them. These seeds resolve entry paths without initializing parsers in the host. The tracer is not loaded per upload or during `next start`. It needs no TypeScript loader, inherited `NODE_OPTIONS`, application environment or model credentials. A production clean-copy upload smoke is required in addition to unit/TypeScript checks. No `pnpm build` during isolated verification: that wrapper migrates whichever DB its environment selects.
- One parser per Node process, reject-busy rather than queue. Cheap storage-enabled/configuration/chat-owner/raw-quota/draft-count checks precede expensive parsing; a second advisory-lock transaction checks full raw + actual derived bytes atomically before reservation. Four request-body uploads and two image decoders remain separately bounded. Put request/time/connection limits at the reverse proxy.
- Each worker has a parent-owned 0700 `chatnest-document-*` scratch directory, restricted environment (`NODE_ENV`, `TMPDIR`, `TMP`, `TEMP` only), empty `execArgv`, V8 old/young heap limits 256/32 MiB and 4 MiB stack, and a 20-second terminate deadline. The parent terminates and removes its scratch directory on success, parser error, zero exit without response, startup failure and timeout. V8 limits are **not** an RSS/native-buffer/network sandbox: deploy in a container with explicit CPU, memory, scratch-disk and log budgets, reserve host headroom and monitor actual limits. No arbitrary file or URL parser input is accepted.
- Hard raw input 64 MiB; ZIP 4096 entries, 128 MiB declared **and actual** inflated total including embedded media, 32 MiB individual XML / 64 MiB total XML. Preflight streams every entry, verifies CRC, rejects duplicate/traversal/encrypted paths, inconsistent local/central headers, hidden/unindexed records, DTD/entities, alternate XML encodings and macro/embedded-object packages. The budget applies before either Office parser.
- PDF text uses `pdfjs-dist/legacy/build/pdf.mjs`, with evaluation, system fonts and external fetching disabled; max 300 pages. `page:N` references are actual PDF pages. Encrypted PDF returns `locked` (no password input/state); scan-only PDF returns `no_extractable_text`; mixed empty pages have explicit warnings. No OCR is performed.
- DOCX references are actual ordered `paragraph:N` or `table:N:row:N:cell:N:paragraph:N`, not fictional pages. Mammoth 1.13.0 `extractRawText` does not accept a transform and loses table positions. The implementation therefore uses the public `convertToHtml` typed `transformDocument` hook to collect pure text, then returns an **empty** tree before conversion, with `externalFileAccess:false`. No source HTML or image conversion is rendered, stored or sent to a model. Text extraction explicitly does not interpret embedded media/charts.
- XLSX uses **streaming** `ExcelJS.stream.xlsx.WorkbookReader`, never `xlsx.load`. Validated XML is re-emitted as a bounded stream with workbook metadata first; original bytes are unchanged. Media was already streamed/drained by preflight and is omitted from the parser-only stream. A fixed empty shared-string table is inserted when absent, avoiding ExcelJS 4.4.0's deferred-worksheet/temp-file data-loss path. This also avoids its worksheet-before-workbook ordering race. A bounded SAX pass resolves every actual workbook worksheet relationship (including custom/absolute part paths), retains real sheet names and date1904, and maps them to canonical parser-only names. Missing, external or unsupported sheet relationships fail explicitly instead of silently dropping a sheet. Macro detection inspects ContentType/relationship metadata and real package entry names, not ordinary document body text. Any library-created temporary worksheets still stay in the private `TMPDIR`; original total XML bounds their aggregate disk budget. Max 50 sheets and 100,000 nonempty cells; `sheet:"name"!A1` refs retain sparse locations. Formula **cached results only**, missing results have an explicit marker; formulas/macros/links are never executed or fetched. Dates are ISO text. Embedded images/charts are not read as visual content.
- CSV preserves actual parsed row numbers, including quoted multiline fields; an undetectable-delimiter warning defaults to comma for legitimate single-column/single-cell files while malformed quotes remain errors; TXT uses UTF-8 line references. DOC/XLS and macro formats must be converted to ordinary supported files. Office encrypted/legacy binary containers request a decrypted modern-format copy; there is no server-side decryption or password storage.
- Persisted extraction is at most 1,000,000 JS characters or 20,000 segments, each at most 4000 characters, with explicit `truncated` status. Discarded content is not secretly retrievable. `UploadAsset.extraction` stores `{status,characters,segments:[{ref,text}],warnings}`; actual JSON UTF-8 byte length is stored as `derivedBytes` (max 8 MiB), and **raw + derived bytes** count in both deployment/user quotas, including pending/deleting reservations. Tiny compressed files therefore cannot create unaccounted persistent text. Migration `0003_document_ingestion` extends the existing table/lifecycle; backup DB extraction and original directory together.
- Upload response adds `size` and `extraction:{status,characters,segments:number,warnings}`; canonical refs remain unchanged. UI shows uploading/reading, text-ready, truncated, locked/no-text or failure states with filename/type/size. Failure retry keeps only an ephemeral browser `File`, never passwords. Locked/scanned/failed attachments are blocked from sending and may be removed/replaced. Original images and editing associations remain preserved.
- A single trusted adapter covers new/history/regeneration/approval/edit context before persistence/title/model calls. Each document receives a JSON-serialized `UNTRUSTED_ATTACHMENT_SOURCE` preview of at most 2000 source characters, asset metadata, real refs, source statistics/status and a text-only/no-OCR/no-media-analysis notice. Repeated canonical refs share a single preview. Preview source text is capped at 100,000 characters across the round; excess context fails explicitly. Server original integrity is stream-verified without retaining large document binaries in model-context memory. Only images require vision. Models without tools get an explicit limited-preview notice, not an implied full read.
- Optional `readAttachment({assetId,startSegment=0,limit=20})` accepts zero-based segment offset and 1..100 segments. Every call rechecks current user, chat ownership, `used` state, and an actual canonical committed message association; draft/public/cross-chat IDs are not tool authority. It returns asset/name/status/warnings/statistics, `segments:[{ref,text}]`, `nextSegment` or null, characters and remaining budget. It returns at most 16,000 source characters per call. One shared server-owned `AttachmentRoundBudget` caps **all attachments together** at 100,000 source characters per model round, seeded by the adapter consuming the actual deduplicated preview text (not a fixed per-asset reservation). Tool reads consume that same remaining budget across every asset. It never skips a partial segment; too little remaining budget for the next segment is explicit rather than an infinite empty page. Model-selected reading is optional, not a keyword/supplier/table pipeline.
- Current stream steps receive actual source text. On a **new request** historical `readAttachment` outputs are model-projected to `HISTORICAL_ATTACHMENT_READ_METADATA` (asset/name/status, character/range metadata, explicit “source text is not replayed; optionally read again” notice). This prevents unlimited historical raw-text replay. Canonical DB/UI output remains unchanged; attachment read cards show human-readable text/ref details. Fresh calls in that request still receive actual source segments.


### Next proxy body envelope and memory budget

Installed Next 16.2.10 uses `experimental.proxyClientMaxBodySize` (the previous `middlewareClientMaxBodySize` name is deprecated). The value is **65mb** to accommodate the app's 64 MiB document + 64 KiB multipart envelope without Next silently truncating to its 10 MB default. Image validation stays 5 MiB, document validation stays 64 MiB, and same-Origin/authentication/application admission remain in place; the proxy is not bypassed. See [official Next proxy body documentation](https://nextjs.org/docs/app/api-reference/config/next-config-js/proxyClientMaxBodySize).

The Next setting applies only to its own proxy buffer. [Vercel Functions impose a 4.5 MB request/response payload limit](https://vercel.com/docs/functions/limitations#request-body-size); **65mb does not raise that platform limit** or make 64 MiB multipart uploads work on Functions. The current local driver is self-hosted only; a cloud deployment needs the private direct-upload adapter described above.

Next clones request bodies **before** route-level admission and its limit is per request, not a global semaphore. Account for these copies in the production container RSS budget, in addition to the four admitted app bodies, parser V8/native buffers and Next itself. Enforce connection/rate/body/concurrency/time budgets at the front proxy too; V8 `resourceLimits` and app admission alone are not an aggregate RSS guard. Deployment limits must be verified on the actual host, not inferred from a successful local parser test.


## AI telemetry content boundary

`instrumentation.ts` registers the AI SDK OpenTelemetry integration globally. In installed `ai@7.0.15`, a registered integration is enabled by default, and input/output recording also defaults on. Every application model call therefore explicitly applies the frozen `server/shared/telemetry.ts` policy: `recordInputs:false` and `recordOutputs:false`. This includes main chat, title generation, text/code/sheet creation and updates, and suggestions (nine calls), not just the top-level chat stream.

The policy retains operational model/usage/timing metadata without recording prompts, attachment previews, document bodies, tool inputs/results or generated content as AI input/output span attributes. Offline tests check all call sites and exercise the installed AI SDK plus OTel against a local mock model/tool and captured span attributes. This is not blanket redaction of application logs, provider-side retention, transport errors or third-party instrumentation; review those separately before deployment.
