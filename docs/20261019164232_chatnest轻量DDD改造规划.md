# ChatNest 轻量 DDD 改造规划

> 时间:2026-10-19
> 前置:《ChatNest 技术栈基座梳理》(同目录)
> 参考:`1207575273/work_nm_tp` 的分层约定(取其形,不取其重);`nikolovlazar/nextjs-clean-architecture` 的 Next 落地形态
> 性质:改造方案,待评审。本文不改动任何代码。

---

## 一、本轮定调

| 项 | 决定 |
| --- | --- |
| 分层 | 平台层 + domain / application / infrastructure 三层,**不做 CQRS** |
| 读写 | 统一走仓储,复杂读由仓储方法返回读模型,**不分 command / query 文件** |
| 契约 | **不建 contracts 包**,前后端同仓天然共享类型 |
| 领域模型 | 贫血:type + 仓储接口 + 纯函数 |
| 一级目录 | 收敛为 `app` / `server` / `public` / `docs` / `deploy` / `tests`,其中 `public` `tests` 是工具链硬要求 |
| Next 项目根 | **保持仓库根不动**(见第三节,这是对前一版方案的修正) |
| 部署 | Vercel 与自托管 Docker **双形态都支持** |

**不做清单**([SKIP]):CQRS 读写分离、contracts 独立包、DI 容器、充血模型、事件溯源、monorepo 拆包、挪动 Next 项目根。
理由统一是 KISS/YAGNI —— 这些在当前规模下维护成本高于收益,需要时再加。

## 二、目标目录形态


## 三、为什么不挪 Next 项目根(对前一版的修正)

前一版方案提出把 Next 根挪到 `web/`,以把一级目录压到 4 个。**查证后撤回**:这个做法在 Next 生态里没有先例。

GitHub 上主流 Next 项目的实际结构:

| 项目 | 顶层 | Next 应用内部 |
| --- | --- | --- |
| `vercel/commerce` | `app components fonts lib` | 官方模板形态,与 ChatNest 现状一致 |
| `calcom/cal.com` | `apps packages deploy docs scripts` | `apps/web/{app,components,lib,modules,server}` |
| `documenso/documenso` | `apps packages docker scripts` | `apps/remix/{app,server}` |
| `formbricks/formbricks` | `apps packages docker docs` | `apps/web/{app,lib,modules}` |
| `twentyhq/twenty` | `packages` | `twenty-front` / `twenty-server` 分包 |
| `t3-oss/create-t3-app` | — | `src/app` + `src/server/{api,auth,db}` |
| `nikolovlazar/nextjs-clean-architecture` | `app src di drizzle public tests` | `app/` 在根,分层在 `src/` |

**四条社区共识**:

1. `app/` 永远位于 Next 项目根(或 `src/app`),**没有项目用 CLI 参数把它挪到子目录**
2. 真要拆 server / web,走 workspace(`apps/*` + `packages/*`),不是单包挪根
3. 服务端代码放 Next 包内的 `server/` 目录 —— t3、cal.com、documenso 都用这个名字
4. 功能切片命名用 `modules/`,DDD 层名(`domain` / `application` / `infrastructure`)在 Next 生态属少数派

**撤回带来的收益**:`outputFileTracingRoot`、tsconfig 双层、Vercel Root Directory 这三个坑全部消失。
`tsconfig.json` 的 `"@/*": ["./*"]` 继续覆盖新目录,**改造不需要动 tsconfig**,P0 从"全量 import 重写 + 改框架根"降级成"文件移动 + 改 import 前缀"。

**与参考实现的一处有意分歧**:`nextjs-clean-architecture` 把仓储接口放在 `application/repositories`。
本方案放在 `domain/<域>/*.repository.ts` —— 接口跟着领域走,application 依赖 domain 的抽象而非自己定义抽象。两种都能跑,选后者是为了让 domain 真正成为依赖的终点。

## 四、平台层的边界(你说的"平台层就是平台层的")

`app/` 下有两类东西,规则不同:

### 4.1 平台层:`app/**/{page,layout,route,actions}.tsx|ts`

**只许放 Next / Vercel 的东西**:

| 允许 | 禁止 |
| --- | --- |
| 路由匹配、`page.tsx`、`route.ts`、Server Action | 任何业务规则 |
| 入参 zod 校验,失败直接 400 | 直接 import `@/server/infrastructure/**` |
| `NextRequest` / `Response` / `after()` / `geolocation()` / `checkBotId()` | 直接碰 drizzle 或数据库 |
| 调 `useCases().xxx()` 并把结果包成 Response | 跨 usecase 自己编排多步流程 |
| 领域错误 -> HTTP 状态码映射 | |

### 4.2 UI 层:`app/_components/**` `app/_hooks/**` `app/_lib/**`

下划线前缀是 Next 的私有目录约定,不参与路由。这里是纯前端,**不得 import `@/server/**` 的任何东西**(类型除外,且只能来自 `server/domain`)。

### 4.3 反向约束

`server/**` **不认识 HTTP**:不 import `next/server`、`next/headers`,不返回 `Response`。
唯一例外在第六节(流式)。

## 五、server 三层职责

### domain/ —— 贫血领域模型

放:实体 type、状态机联合类型、zod schema、**仓储接口**、无副作用纯函数(`canAccessChat` / `canRegenerate`)。
禁:任何 IO、`class` 包业务方法、import 外层。

```
server/domain/
  chat/     chat.types.ts  chat.repository.ts  chat.policy.ts
  message/  document/  vote/  user/
  shared/   ids.ts  errors.ts
```

### application/ —— 唯一的业务编排处

放:UseCase、事务边界、跨聚合协调、权限检查、业务校验。
禁:HTTP 概念、直接 new 数据库/fetch 客户端(靠注入)。

**不分 command / query**。复杂读就在仓储上加方法,让它返回读模型:

```ts
// 不是 list-history.query.ts,而是仓储的一个方法
export interface ChatRepository {
  listSummariesByUser(userId: UserId, cursor?: Cursor): Promise<ChatSummary[]>;
}
```

`ChatSummary` 是 domain 定义的读模型 type,实现里该 join 就 join,该分页就分页。
**好处**:只有一个访问入口,不用记"这个读走哪条路";**代价**:仓储接口会长一些 —— 当前规模下这个代价更划算。

### infrastructure/ —— 适配器

放:仓储实现(drizzle)、LLM 客户端、MCP runtime、Blob / Redis、配置加载、日志。
禁:把 DB 行或第三方字段直接传给 application(必须翻成 domain 模型);在仓储里写业务规则。

## 六、三个需要拿捏的点

### 6.1 Composition Root 是模块级工厂,不是启动脚本

Next 没有 `main.ts`,serverless 每实例独立冷启动。

```ts
// server/composition.ts
import "server-only";
let cached: Container | null = null;

function build() {
  const chatRepo = new DrizzleChatRepository(db);
  return { sendMessage: makeSendMessage({ chatRepo, messageRepo, llm }) };
}

export function useCases() {
  cached ??= build();
  return cached;
}
```

**硬约束**:`build()` 里只能放无状态或可安全跨请求复用的对象。按会话变化的状态一律不进去。

### 6.2 流式 UseCase 返回流,不返回 Response

`send-message` 要产出 SSE。若 UseCase 返回 `Response`,HTTP 就渗进 application 了。

**约定**:UseCase 返回 `UIMessageStream`(AI SDK 的框架类型,不是协议类型),落库副作用由 UseCase 自己完成;平台层只做 `createUIMessageStreamResponse(stream)` 这一步。

这是本项目唯一需要拿捏分寸的地方:**AI SDK 的流类型算框架,允许进 application;`Response` / `NextRequest` 算协议,不允许。**

### 6.3 RSC 也是平台层

`app/(chat)/chat/[id]/page.tsx` 是 Server Component,天然能 await 数据库。
放任它 import 仓储,分层就白做了。**RSC 与 route handler 同级,只能调 usecase。**

## 七、边界强制(已实测验证)

Biome 2.5.2 的 `style/noRestrictedImports` + overrides 够用,**不用引 eslint**。

以下配置我在沙盒实测过:domain 文件 import `@/server/infrastructure/**` 和 `../../**` 都报错,同域内的 `../shared/ids`、`./policy` 不误报,application import infrastructure 不误报。

```jsonc

"overrides": [
  {
    "includes": ["server/domain/**"],
    "linter": { "rules": { "style": { "noRestrictedImports": { "level": "error", "options": { "patterns": [
      { "group": ["@/server/application/**", "@/server/infrastructure/**", "@/app/**"],
        "message": "R1: domain 只放类型 + 仓储接口 + 纯函数,不得依赖外层" },
      { "group": ["../../**"], "message": "R1: 跨层相对导入禁止,一律用 @/ 别名" }
    ] } } } } }
  },
  {
    "includes": ["server/**"],
    "linter": { "rules": { "style": { "noRestrictedImports": { "level": "error", "options": { "patterns": [
      { "group": ["@/app/**", "next/server", "next/headers", "next/navigation"],
        "message": "R2: server 不认识 HTTP 与前端;请求上下文应作为参数传入" }
    ] } } } } }
  },
  {
    "includes": ["app/**"],
```

**验收方式**:每次改规则后放一个故意违规的探针文件,确认 `pnpm check` 报错再删 —— 防止规则静默失效。

## 八、迁移路径

分两大步:**先搬家(P0),再分层(P2)**。不要一个 PR 里同时做,否则 review 不动也回滚不了。

### P0 目录收敛(1 天,纯搬运,零逻辑改动)

只动文件位置和 import 前缀,**不拆层**。`lib/` 按"前端 / 服务端"二分:

| 现在 | 去处 |
| --- | --- |
| `components/` | `app/_components/` |
| `hooks/` | `app/_hooks/` |
| `lib/utils.ts` `lib/types.ts` `lib/constants.ts` `lib/editor/` | `app/_lib/` |
| `artifacts/*/client.tsx` `artifacts/actions.ts` | `app/_artifacts/` |
| `lib/db/` | `server/db/`(P2 再拆进 infrastructure) |
| `lib/ai/` `lib/agent/` | `server/ai/` `server/agent/`(P2 再拆) |
| `artifacts/*/server.ts` | `server/artifacts/` |
| `lib/errors.ts` `lib/ratelimit.ts` `lib/auth-cookies.ts` | `server/shared/` |
| `skills/` `config/` | `server/` 下同名 |
| `tests/unit/*.test.ts` | 就近挪到 `server/` 对应模块旁(`xxx.test.ts` 与 `xxx.ts` 同目录) |
| `tests/e2e` `tests/visual` 及其 fixtures | 留在 `tests/` |
| `vercel-template.json` `.env.example` | `deploy/` |
| `app/` `public/` `next.config.ts` `proxy.ts` `instrumentation*.ts` `vercel.json` | **不动** |

**配套改动**:

- `components.json` 的 aliases 改指 `@/app/_components` / `@/app/_lib` / `@/app/_hooks`
- `next.config.ts` 的 `outputFileTracingIncludes` 路径改为 `./server/config/agent.json` 与 `./server/skills/**/*`
- `server/agent/config.ts` 里读取 `config/agent.json` 的默认路径同步改
- `biome.jsonc` 的 `files.includes` 排除项(`!components/ai-elements` 等)跟着改路径
- **`tsconfig.json` 不用动**(`@/*` 已覆盖)

**import 重写用脚本做**,不要手改:`scripts/migrate-paths.mjs`,按映射表跑正则替换,一次成型。

**验收**:
- `tsc --noEmit` 通过
- `pnpm dev` 起得来,首页可访问
- `pnpm build` 通过,且产物里有 `server/skills/**`(验证 tracing 配置生效)
- e2e 与 visual 全绿(先跑一遍当前基线截图留底)

### P2 切第一个域:chat(2-4 天,收益最大)

目标:`app/(chat)/api/chat/route.ts` 从 525 行降到 100 行以内。

```
server/domain/chat/         chat.types.ts  chat.repository.ts  chat.policy.ts
server/domain/message/      message.types.ts  message.repository.ts
server/application/chat/    send-message.usecase.ts  regenerate-answer.usecase.ts
server/infrastructure/persistence/drizzle/   client.ts  chat.repository.ts  message.repository.ts
server/composition.ts
```

route.ts 改造后:

```ts
export async function POST(request: NextRequest) {
  const parsed = postRequestBodySchema.safeParse(await request.json());
  if (!parsed.success) return new ChatbotError("bad_request:api").toResponse();

  const session = await auth();
  if (!session?.user) return new ChatbotError("unauthorized:chat").toResponse();

  try {
    const stream = await useCases().sendMessage({
      ...parsed.data,
      userId: session.user.id,
      userType: session.user.type,
      hints: geolocation(request),
      signal: request.signal,
    });
    return createUIMessageStreamResponse({ stream });
  } catch (error) {
    return toHttpError(error);
  }
}
```

**留平台层**:`checkBotId` / `geolocation` / `after()` / Response 组装。
**进 application**:额度判断、归属校验、消息三分支组装、模型解析、runtime 装配、流编排、落库。

**验收**:新增 `send-message.usecase` 单测(mock 仓储,不起 HTTP、不调真模型);e2e 与 visual 行为不变;route.ts < 100 行。

### P3 推平其余域(每域 0.5-1 天)

顺序:`document` -> `vote` -> `history` -> `suggestion` -> `user`,每域一个 PR。
`server/db/queries.ts` 逐步掏空,最后删除。

**验收**:`queries.ts` 不存在;`app/**` 无一处直连持久化(R3 自动保证)。

### P4 双形态部署

| 形态 | 做法 |
| --- | --- |
| Vercel | 仓库根即项目根,无需 Root Directory 设置;`vercel.json` 保持 `{"framework":"nextjs"}` |
| 自托管 | `output: "standalone"` + `deploy/Dockerfile` + `deploy/compose.yaml`(app + postgres + redis) |
| 共同 | 新增 `app/api/health/route.ts`,检查 DB / Redis 可达性 |
| 共同 | `instrumentation.ts` 的 serviceName 从 `chatbot` 改成真实服务名 |

**自托管前必须先做无状态化**:`server/agent/browser-session.ts` 的进程内状态迁到 Redis 或独立 worker,否则多实例直接失效。单实例自托管可以先不动。

## 十、开工前要你拍板的一件事

**是否还跟上游 `vercel/chatbot`?**

P0 把 `components/` `hooks/` `lib/` 全部改名移位,之后 merge 上游会大面积冲突。

- 要跟 -> P0 缩到最小(只建 `server/` 并搬 `lib/{db,ai,agent}`,`components/` `hooks/` 原地不动),一级目录 8 个
- 不跟 -> 按本文执行,一级目录 6 个(其中 `public` `tests` 是工具链硬要求)

部署目标已确认双形态,P4 照做,不需要额外决策。
