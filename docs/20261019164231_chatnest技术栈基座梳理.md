> 时间:2026-10-19
> 范围:当前仓库 `D:\a_dev_work\chatnest`,分支 main,基线 commit `b51c51d`
> 目的:为后续"轻量 DDD 分层改造"建立事实基础。本文只描述现状,不含改造方案。

---

## 一、一句话定性

本项目是 `vercel/chatbot` 官方模板(上游基线 `c2f8235`)的业务化分叉,形态为 **Next.js App Router 全栈单体**:
前端、API、业务编排、数据访问同处一个 Next 进程与一次部署,**路由处理器本身承担服务层职责**,没有独立的 application / domain 分层。

## 四、分层现状(关键事实)

### 4.1 没有 application 层,编排在 route 内联

`app/(chat)/api/chat/route.ts`(525 行)单个 POST handler 内串联:

1. BotID 校验(`checkBotId`)
2. 入参 zod 解析(`postRequestBodySchema`)
3. 会话鉴权(`auth()`)+ 用户类型额度(`entitlementsByUserType`)
4. IP 限流(`checkIpRateLimit`)
5. 消息配额查询(`getMessageCountByUserId`)
6. 会话归属校验 + 建会话 + 标题生成(`saveChat` / `generateTitleFromUserMessage`)
7. 三种消息组装分支:常规 / 工具确认回流(`applyToolApprovals`)/ 重新生成(`prepareRegeneration`)
8. 模型解析与能力查询(`getRuntimeModels` / `getCapabilities`)
9. MCP Agent runtime 装配(`createAgentRuntime`)+ 浏览器工具(`createBrowserTools`)
10. SSE 流编排、等待态推送、9 秒健康检查定时器
11. 落库(`saveMessages` / `replaceRegeneratedAnswer`)+ `after()` 善后
12. resumable-stream 续流

该文件 import 了 13 个 `lib/db/queries` 导出函数,直接操作持久化。

### 4.2 数据访问是单文件平铺

`lib/db/queries.ts`:680 行,28 个导出函数,覆盖 7 张表的全部读写。
顶部有 `server-only` 守卫(全仓唯一一处)。无 repository 接口,无按领域拆分,调用方直接 import 具体函数。

### 4.3 模块边界无机器强制

- 边界仅靠目录约定与 `server-only`(仅 queries.ts 一处)
- `tsconfig.json` 只有 `@/*` 一条别名,没有分层别名
- `biome.jsonc` 未配置任何 import 限制规则
- 结论:任何文件都可以 import 任何文件,层次腐化无护栏

### 4.4 有状态单例

`lib/agent/browser-session.ts`(317 行)在模块作用域维护浏览器会话、控制修订与确认状态,属进程内存状态。
DEVELOPMENT.md 已自认:"单进程内存状态,重启会丢失页面并拒绝旧确认"。

### 4.5 配置读取分散

`process.env.X` 在 `lib/` 与 `app/` 中散落 14 个变量、约 26 个读取点,无集中 schema 校验。
唯一做了结构化校验的是模型连接:`lib/ai/model-connection.ts` 对 `OPENAI_BASE_URL` 做协议 / 凭据 / 路径后缀检查并抛错。

## 五、技术栈清单(按关注点)

### 5.1 AI / Agent

| 包 | 版本 | 用途 |
| --- | --- | --- |
| `ai` | 7.0.15 | Vercel AI SDK 核心:`streamText` / `createUIMessageStream` / 多步工具循环 |
| `@ai-sdk/openai` | 4.0.7 | OpenAI 及兼容端点 provider |
| `@ai-sdk/react` | 4.0.16 | 客户端 `Chat` 实例与 SSE 消费 |
| `@ai-sdk/mcp` | 2.0.7 | MCP 客户端(`createMCPClient`) |
| `@modelcontextprotocol/sdk` | 1.29.0 | MCP 协议底座 |
| `@playwright/mcp` | 0.0.83 | 浏览器能力(微软官方 MCP server) |
| `@ai-sdk/otel` | ^1.0.15 | 模型调用链路追踪 |

**模型接入**:`lib/ai/model-connection.ts` 支持双形态 —— `MODEL_PROVIDER=openai`(直连 OpenAI/兼容端点)或 `gateway`(Vercel AI Gateway)。未声明 provider 时,存在 OpenAI Key/地址/模型任一则判定直连。

**Agent 运行时**:`lib/agent/runtime.ts` 读 `config/agent.json` -> 并发连接各 MCP server -> 按 `allowedTools` 白名单装配 ToolSet -> 合并 skill 工具(`loadSkill` / `readSkillResource`)。工具统一命名 `<server-id>__<remote-tool-name>`;`autoApproveTools` 之外的工具需用户确认。

**内建工具**:`lib/ai/tools/` 下 `create-document` / `update-document` / `edit-document` / `request-suggestions` / `get-weather`(weather 未对 Agent 开放)。

### 5.3 认证与安全

## 七、与参考项目 work_nm_tp 的基座差异

| 维度 | work_nm_tp | ChatNest 当前 |
| --- | --- | --- |
| 仓库形态 | pnpm monorepo(apps/server + apps/web + packages/contracts) | 单包 |
| 前后端 | 物理分离(Hono 后端 + Vite 前端,端口 41421/41422) | 同进程(Next 全栈) |
| 分层 | interface / application / domain / infrastructure 四层 | 无分层,route + lib 两段 |
| 读写模型 | CQRS:写走 Repository,复杂读走 `*.query.ts` | 统一 `queries.ts`,无区分 |
| 依赖注入 | Composition Root 在 `main.ts` 手动注入,不引容器 | 无,直接 import 具体实现 |
| 边界强制 | eslint-plugin-boundaries R1/R2 + no-restricted-imports R3 | 无 |
| 契约 | `packages/contracts` 单一真源,只许 interface 层 import | 无,`lib/types.ts` 与 DB schema 混用 |
| 领域模型 | 贫血:type + zod + repository interface + 纯函数 | 无独立 domain,drizzle schema 直接当模型 |
| 常驻 | pm2 fork 单实例 + `/health` | Vercel serverless,无健康端点 |
| 测试 | vitest 1512 单测 + 33 集成 + 82 前端 | node:test 7 文件 + playwright + python 视觉 |

**可直接借鉴的三条**:四层目录与各层 README 约定、CQRS 的"写走仓储 / 复杂读直连"显式例外、边界的机器化强制。

**不宜照搬的两条**:monorepo 拆包(Next 全栈下收益低于成本)、Composition Root 单例注入(serverless 每请求独立实例,需改为模块级工厂)。

## 八、现状风险清单

| 级别 | 项 | 证据 | 影响 |
| --- | --- | --- | --- |
| 高 | 业务逻辑不可单测 | `api/chat/route.ts` 525 行内联编排 | 只能通过 HTTP 黑盒测,回归成本高 |
| 高 | 进程内存状态 | `lib/agent/browser-session.ts` | 多实例部署直接失效,无法水平扩展 |
| 中 | 无 env 启动校验 | 26 处散落 `process.env` | 配置缺失在运行时才暴露 |
| 中 | 无边界强制 | biome 未配 import 限制 | 分层改造后仍会腐化 |
| 中 | 类型与运行时不匹配 | `@types/react` 18.3.31 vs `react` 19.2.7 | 上游遗留,React 19 新 API 类型可能缺失或报错 |
| 低 | OTel serviceName 未改 | `instrumentation.ts` 为 `"chatbot"` | 多服务共用后端时无法区分 |
| 低 | 无容器化 / 健康端点 | 仅 `vercel.json` | 自托管需从零补 |

## 九、结论

基座本身的技术选型现代且一致(Next 16 + React 19 + AI SDK 7 + Drizzle + Biome),**问题不在选型,在组织方式**:
缺 application / domain 两层,业务规则寄生在路由处理器里;缺边界强制,改造完也会退化;有进程内状态,无法水平扩展。

后续改造方案见同目录《ChatNest 轻量 DDD 改造规划》。
