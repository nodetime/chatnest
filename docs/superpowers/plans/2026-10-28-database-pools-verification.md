# 数据库连接池修复验收

## 根因与修复

| 项目 | 结果 |
|---|---|
| 原故障 | Next开发路由/热更新重新求值模块级postgres构造器，主仓储、上传和两个设置仓储各自建立池；发生Postgres 53300（too many clients already），导致上传后的审批续跑失败 |
| 修复 | 同一Node进程的版本化global Symbol复用连接；ORM及两个设置仓储共用最多4连接，上传列名转换池最多2连接；空闲20秒回收，连接建立超时10秒 |
| 配置隔离 | 不无限按URL缓存池，不把既有请求切到另一数据库；数据库URL变化要求重启。连接标签包含进程PID，预算测量不会把其它应用/副本混进来 |
| 不变部分 | 上传列名camelCase但JSON原样，原事务/advisory lock/属主/审批/Agent调度不变；迁移保留独立max1连接，未新增表/迁移 |
| 部署边界 | 6是每Node应用进程上限，不是整个集群上限；总预算仍须乘实例/进程数，必要时使用外部连接池。一次部署重启用于加载修复，不作为修复机制 |

## 调试过程

修复前先记录两次失败：直接操作冷页面隐藏file input未触发上传，随后实际上传探针成功；第二次在审批续跑处被53300阻断。上传自动化改为点击真实附件菜单、等待可用后通过原生文件选择器上传，避免绕过界面就绪条件。未改变上传权限或Agent流程。连接池VM/PID回归先红后绿；最终以不重启的热更新和真库并发测量验收，不靠扩大Postgres上限。开发热更新探针初轮出现页面异常后保留失败记录并复测，最终完整8轮无异常。
